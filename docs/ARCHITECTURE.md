# Backend foundation

Composition is owned by `apps/server/src/app`: validated environment, database resource lifecycle,
Fastify creation and signal shutdown. `interfaces/http` maps the application health result to HTTP.
`application/health.ts` depends on DatabaseHealth and Broker ports; PostgreSQL and PaperBroker implement
these contracts in infrastructure. `domain/tradingSafety.ts` is a pure configuration gate.
Quote and Portfolio are provider-independent domain read models; database records are not domain entities.

Public shared API contracts live in `@ai-trader/contracts`. Shared strict compiler configuration
lives in `@ai-trader/config`. Package exports prevent imports of package implementation paths.
ESLint restricts outward dependencies from domain/application. Manual and strategy paper execution are
opt-in; deterministic daily Strategy v1 and offline backtesting are implemented. AI remains unimplemented. Read APIs, deterministic risk and execution are described below.

Startup checks the database before listening. Runtime health rechecks connectivity with bounded
connection/query timeouts and returns 503 on failure. Logs omit raw environment and driver errors.
SIGINT/SIGTERM close Fastify and the PostgreSQL pool, with a ten-second shutdown deadline.

Paper is the default. `hasLiveTradingOptIn` requires BOTH explicit switches, but it is only a
necessary configuration condition, never order authorization. This build rejects ALL live broker
configurations. The health Broker port exposes mode identity; the separate MarketBroker port owns read-only quotes.

PostgreSQL 17 schema uses UUID primary keys, timestamptz instants, decimal strings mapped from
numeric(24,8), explicit three-letter currency codes, and shares as quantity units. Prices and money
are expressed in the recorded currency; no JS float arithmetic exists. Positions currently represent
long holdings. Score is 0–100; confidence is 0–1. Legacy proposal risk text is retained; execution stores a full risk audit.
Orders reference proposals with RESTRICT deletion and allow BUY/SELL only; proposals also allow HOLD.
Order price is nullable during preparation; requested_price records the server quote, not the MARKET
fill price. The execution repository explicitly updates updated_at and writes proposals/orders,
cumulative order_fills, execution deltas and the broker position mirror. Existing rows remain readable by old columns.

Migrations are checked-in SQL generated by Drizzle Kit and applied only by explicit command.
The runtime image carries a compiled migration entrypoint, not development dependencies.
Compose uses an existing external named volume and exposes only loopback port 3200 for HTTP.
An existing database must remain under its existing Compose project/service/network ownership.

## KIS paper market data

`app/server.ts` calls `createRuntimeApp`, which creates the KIS adapter and injects application ports
and a paper portfolio RiskContextProvider into `createApp`. `createApp` registers application use cases.
The application owns MarketBroker and safe BrokerError contracts; domain Quote has no provider fields.
HTTP routes depend on application use cases; shared QuoteResponse/BrokerStatusResponse describe the API.
The existing database `/health` remains independent of KIS availability.

The adapter contains a bounded fetch client, Zod response schemas, a token provider and quote mapping.
Only `https://openapivts.koreainvestment.com:29443` is accepted at startup and at the transport boundary.
Redirects are rejected and each request has a ten-second timeout. No automatic HTTP retry is performed.
App key/secret come only from validated environment. Account variables are accepted and passed through
Compose; account number/product code are passed to the portfolio adapter only for account queries.
They are not needed for token/quote requests.

Tokens are process-local, reused until 60 seconds before expires_in (measured from issuance start).
Concurrent issuance shares one Promise; failure clears it for a later request. Authentication rejection
invalidates the corresponding cached token for the next request without replaying the failed request.
Restarting or using multiple server processes creates separate caches; Redis and distributed coordination
are outside this phase. Provider bodies, credentials and raw exceptions are never logged or returned.

`GET /api/v1/market/:symbol/quote` validates exactly six ASCII digits and maps KIS price/change to KRW
strings, changeRate to percentage strings (1.5 means 1.5%), volume to cumulative share strings.
`timestamp` is server receipt time in UTC, NOT trade time or a guarantee of market-data freshness.
`GET /api/v1/broker/status` reports provider, paper mode, credential completeness and reachability.
It returns HTTP 200 for an inspected status, including failed connectivity; failure adds a safe error code.
With credentials it performs a real 005930 quote request each time, sharing the token cache.
It does not merely infer reachability from a locally cached token. Unconfigured status makes no request.

Quote errors distinguish invalid_symbol (400), configuration_error (503), authentication_error (502),
provider_unavailable (503), provider_invalid_response (502). Unexpected errors are sanitized to 500.
An upstream authentication failure is 502 rather than implying the API caller's authentication failed.
The separate OrderBroker port owns paper buy/sell and fill queries; quote routes never submit orders.

## KIS paper account portfolio

`GET /api/v1/portfolio` → application `createPortfolioQuery` → AccountBroker → KIS portfolio adapter.
`createRuntimeApp` constructs one `createKisBroker`; quote, portfolio and risk reads share `kisSession`
and the unchanged token provider. HTTP routes share a sanitized broker error handler, with no
infrastructure imports. Public PortfolioResponse/PositionResponse mirror the domain read models.
The transport exposes body and continuation metadata only inside infrastructure.

KIS uses paper transaction VTTC8434R and all-balance INQR_DVSN=00, matching the official legacy
balance sample's all-balance option. Current official examples also document 02 as symbol-level;
its previous use alone does not establish the cause of an upstream failure. Account configuration is validated
as 8-digit CANO and 2-digit ACNT_PRDT_CD on use; missing accounts do not break existing quote/status.
Zod validates all required financial strings, row fields and account summary before mapping.
No DB read/write, migration, balance caching or order authorization is introduced.

`cash` means deposit balance (`dnca_tot_amt`), `totalEvaluation` means `tot_evlu_amt`, purchase cost
means `pchs_amt_smtl_amt`, valuation P/L means `evlu_pfls_smtl_amt`. Amounts/prices are KRW, quantities
are shares, rates are percentages, all represented as strings. Total P/L rate uses exact BigInt decimal
arithmetic with two-place half-away-from-zero rounding. See decision 0002 for zero-cost semantics.
Position fields explicitly map pdno/prdt_name/hldg_qty/ord_psbl_qty/pchs_avg_pric/prpr/evlu_amt/
evlu_pfls_amt/evlu_pfls_rt. Zero-quantity historical rows are excluded from active positions.

F/M response continuation triggers an N request with returned cursors, spaced one second apart.
All pages are validated and combined; account totals are never summed. Repeated cursors, duplicate
symbols, changed summary values, invalid/missing continuation metadata or exceeding 20 pages fail
closed with provider_invalid_response. Pagination is not a guaranteed atomic account snapshot.
No partial portfolio is returned after any failure. Missing/empty summary is account_unavailable (503);
invalid fields are provider_invalid_response (502). Existing configuration/auth/provider error mapping
is reused. Unknown KIS business errors remain provider_unavailable; no raw message is exposed.
Portfolio HTTP responses use Cache-Control: no-store. Account values never appear in logs.

Verified balance query parameters (official sources checked 2026-09-16):

| Field | Value |
| --- | --- |
| Endpoint | GET /uapi/domestic-stock/v1/trading/inquire-balance |
| Paper TR ID | VTTC8434R |
| CANO / ACNT_PRDT_CD | Configured 8-digit account / 2-digit product code |
| AFHR_FLPR_YN / OFL_YN | N / empty string |
| INQR_DVSN / UNPR_DVSN | 00 / 01 |
| FUND_STTL_ICLD_YN / FNCG_AMT_AUTO_RDPT_YN | N / N |
| PRCS_DVSN | 00 |
| CTX_AREA_FK100 / CTX_AREA_NK100 | Empty initially, returned cursors for continuation |

Sources: [official legacy all-balance sample](https://github.com/koreainvestment/open-trading-api/blob/main/legacy/Sample01/kis_domstk.py)
and [current official balance function, including demo TR ID](https://github.com/koreainvestment/open-trading-api/blob/main/examples_llm/domestic_stock/inquire_balance/inquire_balance.py).
The current function demonstrates INQR_DVSN=01 and documents 01/02; the requested all-balance
preference selects the legacy sample's 00. No automatic parameter retries are attempted. Duplicate
symbols still fail closed rather than silently dropping or double-counting rows.

For a non-zero rt_cd, kisSession emits an injected diagnostic containing provider=kis, operation,
transactionId, httpStatus and msgCode. Runtime composition sends it to the structured warning logger.
Balance uses inquire_balance/VTTC8434R; quotes use inquire_price/FHKST01010100. Operation/transaction
identifiers come from a fixed endpoint/TR pair allowlist; unknown pairs become unknown/UNRECOGNIZED,
never arbitrary paths or query strings. The transport observes parsed bodies before HTTP error mapping,
so valid non-zero KIS envelopes on 4xx/5xx are also diagnosed. Non-JSON/empty error responses retain
their status-based generic errors and produce no invented message code. Token issuance does not use
this session response observer. Authentication handling and automatic retry behavior are unchanged.

A request that never receives an HTTP response (the 10-second `AbortSignal.timeout` firing, DNS
failure, connection refused) also emits a diagnostic: httpStatus 0 with msgCode TIMEOUT or
NETWORK_ERROR, distinguished by the abort reason's DOMException name. This lets operators tell a
transport-level failure apart from a provider-returned rejection using only the structured log.
Only eight-character KIS-shaped codes (3 letters/5 digits or 4 letters/4 digits) pass; missing or
malformed codes become UNRECOGNIZED. Codes containing configured credentials/account number or the
current access token become REDACTED. The provider body, msg1, URL/query, account identifiers,
DATABASE_URL, request headers and credentials never enter this event. HTTP error contracts remain generic; auth failures still invalidate
the token, and risk evaluation remains fail closed. Diagnostics do not establish that 00 resolves the
reported production failure until the next actual provider response is observed.

## Deterministic Risk Engine v1

**No order may bypass Risk Engine.** The required path is
`TradeProposal → RiskEngine → RiskDecision → Execution → Broker`.
Risk approval alone is not execution: the debug evaluation endpoint reserves nothing and cannot
submit. The execution application supplies additional account/session/persistence guards below.

`domain/risk` owns pure `evaluateRisk(proposal, context, policy)`, proposal/context models, validation
and an immutable default policy (`version: v1`). Public RiskDecision, rejection reasons and HTTP
request contracts live in `@ai-trader/contracts`. Domain has no DB, HTTP, KIS, Fastify or AI calls.
Amounts are KRW, quantity is shares, rates/confidence are 0–1 ratios. Decimal input is bounded to
numeric(24,8): 16 integral digits and up to 8 fractional digits. BigInt fixed-scale products and
cross multiplication preserve exact comparisons, including products with 16 fractional places.
Scientific notation, whitespace, nonfinite values and excess precision are rejected, never rounded.
Proposal timestamps use canonical UTC ISO strings with milliseconds. No current clock is read in domain.

BUY defaults: confidence >= 0.70; proposed order notional <= 10% of total equity and <= available
cash; fewer than 5 open positions; daily realized P/L strictly greater than -2% of equity;
fewer than 3 consecutive losses; kill switch disabled. All relevant failures are collected in stable
order, including other failures when kill switch is enabled. Invalid proposal/context/policy return
INVALID_PROPOSAL/INVALID_CONTEXT/INVALID_POLICY and cannot approve. Positive equity, nonnegative
available cash and safe nonnegative integer counters are required. Malformed values prevent only
checks dependent on those values, not independent validation or kill-switch rejection.

V1 exposure is incremental order notional, not aggregate existing symbol exposure. Every BUY is
conservatively treated as a new symbol at the position cap; no additional-purchase exception exists.
SELL skips all BUY controls (including confidence threshold and kill switch), but still requires
valid proposal, context and policy. SELL approval does NOT verify holdings, available sell quantity,
whole-share lots or absence of short selling. The execution application checks these separately,
as well as quote receipt age, session and account serialization. Market slippage/fees are not modeled
by this policy; a server quote is an estimate, not a maximum fill price.

`application/risk` orchestrates an injected RiskContextProvider and clock. Its evaluation record
captures proposal, full versioned policy, copied context, decision/reasons and evaluation timestamp;
no DB persistence is added. Provider failures propagate to a sanitized HTTP 503, never approval.
The production paper provider is `application/paperRiskContext.ts`, built against AccountBroker.
Each evaluation reads the portfolio and maps cash → cash, totalEvaluation → totalEquity and
positions.length → openPositionCount. Existing Portfolio.cash remains deposit balance, not verified
buying power; paper v1 explicitly uses it as the risk cash proxy. No extra Portfolio model is introduced.
The account-scoped Trade Ledger supplies dailyRealizedPnl and consecutiveLosses from confirmed
execution history. TRADING_KILL_SWITCH_ENABLED supplies the operational switch in both debug risk
and order execution. Missing ledger data never defaults to zero. Valuation P/L is never realized P/L.
See decision 0006, which supersedes the placeholder history in decisions 0004 and 0005.

The provider validates risk-consumed portfolio fields at runtime: nonnegative cash, positive equity,
an array of active positions with valid six-digit symbols and positive quantities, without duplicate
symbols. Financial values use the domain's exact bounded decimal parser. Malformed input returns null
and the use case rejects with INVALID_CONTEXT. KIS adapter validation still validates the full upstream
response. Adapter/provider exceptions propagate to the sanitized HTTP 503 response. No cached or
initial account balance replaces missing data. There is no context cache; executions persist the inputs needed to reproduce loss history.

`POST /api/v1/risk/evaluate` accepts only symbol, BUY/SELL side, quantity, estimatedPrice and confidence
as strings. The server stamps createdAt. Clients cannot supply context or change policy. Invalid
HTTP shape is 400; semantic proposal rejection is a RiskDecision with 200 when context is available.
Responses contain only the decision and use Cache-Control: no-store. The route calls the application
use case and performs no risk calculations or broker calls. Production follows
`server.ts → createRuntimeApp → createApp → application risk evaluation → paper portfolio provider
→ AccountBroker/KIS portfolio → RiskContext → RiskEngine`. `createApp` requires explicit dependencies,
including RiskContextProvider; missing providers fail at construction rather than becoming null.
Tests can explicitly inject an unavailable provider, but production has no null-provider default.
Human-operated paper execution uses authoritative KIS buying power and the same ledger/switch as
debug risk. Missing repository returns unavailable context; malformed/incomplete ledger throws and
fails closed. The production server always injects the account-scoped PostgreSQL repository.

## KIS Paper Order Execution v1

`POST /api/v1/orders` → application/orders → server quote + account/buying power → TradeProposal →
RiskEngine → persisted RiskDecision → durable SUBMITTING → OrderBroker → KIS paper order → stored result.
Routes only validate/map HTTP and invoke application services. `server.ts` constructs the Drizzle
repository, scoped by a hash of the configured paper account, and `createRuntimeApp` injects it.
Enabled execution without a repository fails startup. Defaults disable execution; a separate bearer
token protects every order route. Live URLs and live broker mode remain prohibited.

The request allows only six-digit symbol, BUY/SELL, positive integer quantity, MARKET and confidence.
Clients cannot send estimatedPrice, context or risk policy. The application fetches a fresh server
quote and records it as requestedPrice. BUY uses KIS nrcvb_buy_amt/nrcvb_buy_qty, excluding margin and
overseas funds; SELL requires available holdings. Existing deterministic policy values are unchanged.
Orders are admitted weekdays 09:00–15:20 Asia/Seoul (exclusive end); KIS handles holidays/suspensions.
Quote receipt age must be <=10 seconds, including after the durable transition. Receipt time is not
exchange last-trade time; this does not guarantee freshness of the upstream trade or market fill price.

Every UUID Idempotency-Key is unique within the execution account. A transaction reserves the key
and proposal before external reads. Replays return the original record; changed payloads conflict.
A partial unique index allows only one unresolved order per account, across processes/restarts.
Risk audit stores proposal, context, versioned policy, decision, timestamp and pre-order holdings.
SUBMITTING must commit before the only order POST. Any ambiguous transport/receipt failure becomes
UNKNOWN; a result-write failure leaves SUBMITTING. Neither state is automatically resubmitted.
This protects this application's orders; simultaneous manual orders in HTS/other clients are outside
its reservation scope and must be avoided during the checkpoint.

`GET /api/v1/orders/:id` reads persisted state. `POST /api/v1/orders/:id/reconcile` reads KIS cumulative
fills and portfolio, validates order identity/quantity and monotonic filled amounts, then atomically
persists order state, a deduplicated cumulative order_fills snapshot and absolute positions.
Acceptance is not a fill. FILLED/CANCELLED orders remain blocking until broker holdings agree with
pre-order quantity plus/minus confirmed fills. Replaying a terminal synchronized order cannot overwrite
later positions. Fill snapshots are not individual exchange execution IDs or fee/tax accounting. Positive cumulative
increments also create executions in the same transaction; the ledger below derives gross realized P/L.

UNKNOWN/SUBMITTING without a broker ID requires operator confirmation and an explicit brokerOrderId
on reconciliation; the server validates date/symbol/side/quantity and never guesses a matching order.
A lost acknowledgement without an identifiable broker order, or a crash in PREPARING, stays blocked
for manual investigation. No timed unlock, automatic retry, cancellation API or background poller exists.
Do not clear the blocker or use a new key to retry an uncertain broker submission.

Current official paper APIs: order-cash BUY VTTC0012U / SELL VTTC0011U, inquire-psbl-order VTTC8908R,
inquire-daily-ccld VTTC0081R (recent orders, within three months). MARKET sends ORD_DVSN=01 and
ORD_UNPR=0, KRX exchange. Fill pagination is bounded and fails closed rather than returning partial data.
New operations use the same secret-safe diagnostic allowlist. No raw broker body/message is persisted.
See [deployment, API and recovery runbook](PAPER_ORDERS.md) for migration and actual-account verification.


## Execution & Trade Ledger v1

The existing protected explicit reconciliation route owns synchronization for unfilled, partial,
filled, cancelled and UNKNOWN orders. There is no background scheduler. UNKNOWN recovery retains
operator-confirmed identity checks and never re-submits an order. Acceptance creates no execution.
Cumulative quantity/amount must increase together; amount-only corrections, regression, fractional
shares and impossible partial statuses are rejected pending investigation.

`domain/tradeLedger.ts` is a pure ordered projection over `LedgerExecution` facts. The PostgreSQL
repository writes positive quantity/amount differences to `executions` with account, order, side,
symbol, KRX trade date, cumulative totals and observation time. A unique order/cumulative-quantity
key plus optimistic order version prevents double posting. Order state, execution, cumulative
snapshot and position mirror commit or roll back together. Observation time is not exchange fill time;
one delta can represent several exchange fills. The original cumulative snapshots remain available.

The ledger reader uses one SQL statement snapshot and verifies each delta and final cumulative totals
against its order. It orders by durable order creation time/ID then cumulative quantity, consistent
with the account's one-unresolved-order constraint. Missing or inconsistent executions fail closed.
Moving-average acquisition cost is tracked separately from the broker's current position valuation.
BUY adds actual gross amount; SELL allocates proportional cost, retaining 8-decimal division residual
in remaining shares until final disposal. BigInt arithmetic avoids floating-point money calculations.
Daily gross realized P/L sums SELL proceeds minus allocated acquisition cost on Asia/Seoul order date
(KRX cash orders do not carry overnight). Fees and taxes are not available in this query and are excluded;
this is not a broker net settlement/tax ledger. The immutable deltas reproduce the projection exactly.

Consecutive losses count net losing SELL orders, combining their partial executions. BUY does not
reset the streak; a profitable or breakeven SELL resets it. The streak persists across trading days,
while daily P/L resets at Seoul midnight. Partial SELL P/L appears immediately; the account remains
reserved until terminal synchronization. No-fill cancellations/rejections create no ledger events.

Risk reads this ledger on every evaluation and requires its open quantities to match the fresh broker
portfolio across all symbols. An untracked holding or sale without acquisition history rejects context;
there is no implicit opening-cost estimate. Exclusive use of this account by this system remains required:
quantity checks cannot discover an external round trip ending at the same quantity. The ledger covers
this system's tracked KIS paper orders, not arbitrary HTS history or corporate actions.

Migration 0002 adds executions and backfills one explicitly marked cumulative execution for each
existing account-scoped order with positive confirmed fills and broker identity/date. It preserves
orders and order_fills, does not invent historical exchange fills, and requires no KIS order request.
Invalid/incomplete history remains detectable by the reader. Historical sales with missing BUY basis
require investigated history repair; deployment must not reset history to admit orders.
See [Execution & Trade Ledger decision](decisions/0006-execution-trade-ledger-v1.md) and the runbook.

## Deterministic Strategy v1 and daily backtesting

`domain/strategy` owns validated regular-session OHLCV, EMA20/60, Wilder RSI14/ATR14, volume ratio,
explicit-universe liquidity screening, signal conditions and ATR/allocation sizing. No clock, network,
DB or broker enters this domain. Financial sizing uses the existing fixed-scale decimal functions;
indicators use bounded finite JS numbers. Shared candle/dataset/request and order provenance types
live in `@ai-trader/contracts`. Existing TradeProposal and Risk Engine contracts are reused unchanged.

`POST /api/v1/strategy/evaluate` is registered inside the existing bearer-protected order route scope.
It accepts complete historical daily data and optionally one executeSymbol. Application orchestration
reads the paper portfolio and ledger-backed RiskContext, evaluates each symbol lexically, and returns
signals plus risk audits. Evaluation alone cannot submit. An explicit selected approved signal enters
`OrderServices.submit`, which re-fetches quotes, holdings and buying power and evaluates risk again.
Execution remains disabled by default. No timer, AI path or historical KIS fetch is added.
The endpoint requires the order repository/service and token even for read-only evaluation.

A SHA-256-derived UUIDv8 identity binds strategy ID/version, symbol and completed bar, deliberately
excluding side, quantity and config to prevent re-evaluation from acquiring a new retry key. Existing
account-scoped reservation/unknown-state handling remain authoritative. Changed payload under the
same identity conflicts. Replay after portfolio changes may return no new signal or fail closed;
original orders remain available through GET /orders/:id. Strategy metadata, selected-symbol candles,
sizing account, configuration identity and full-input digest persist in existing request_payload JSONB.
No migration is needed. The proposal reason identifies strategy entries; manual entries retain human_api.

`application/backtest` uses the same indicators, screener, strategy, risk and ledger projector with
isolated in-memory state. A close signal becomes a pending proposal; next-session open marks and
slippage determine the fresh execution risk context. Exact costs enter BUY basis and SELL proceeds
in the simulation ledger. Production KIS ledger remains gross because its fee/tax inputs are unavailable.
All filled simulated orders must have an approved risk decision and sufficient cash/holdings.
Full inputs, settings, close evaluations, execution audits and equity history are emitted as JSON.
Only report ratios and indicators use floating point. Final signals are left unfilled and open holdings
marked to the final close; no invented terminal liquidation occurs.

Input session calendars are explicit and must match all universe histories; no missing bars are
interpolated. This cannot detect omissions in an incorrectly supplied calendar. Paper evaluation
rejects future or older-than-four-day closes. Submission additionally requires the next calendar
weekday, conservatively rejecting signals carried across weekday holidays. Dataset close is modeled
at 15:30 Seoul and open at 09:00; special sessions are unsupported. The existing execution layer still
checks its own 09:00–15:20 window and quote receipt freshness. See [Strategy runbook](STRATEGY.md) and
[decision 0007](decisions/0007-deterministic-strategy-backtest.md) for definitions and limitations.
