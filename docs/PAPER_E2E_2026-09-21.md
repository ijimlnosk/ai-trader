Before deployment, `/health` returned 200 with a connected database and paper mode; actual KIS
portfolio returned 200. Broker status reported unreachable and quote returned 503. Diagnostics
recorded `inquire_price`, HTTP status 0 (no provider HTTP response).

The quote endpoint, TR ID `FHKST01010100`, and `FID_COND_MRKT_DIV_CODE=J` /
`FID_INPUT_ISCD=005930` agree with the
[official KIS example](https://github.com/koreainvestment/open-trading-api/blob/main/examples_llm/domestic_stock/inquire_price/inquire_price.py).
This comparison does not establish the cause of the transport failure.

A subsequent read-only diagnostic issued fill, balance and quote reads immediately in succession.
The fill succeeded; balance and quote returned HTTP 500 / `EGW00201`. The
[official KIS repository](https://github.com/koreainvestment/open-trading-api/blob/main/backtester/examples/README.md)
identifies this as exceeding per-second transaction limits. Diagnostic requests were changed to
use 1.5-second spacing for follow-up verification. No automatic order retry, policy change or
broker-adapter bypass was introduced. The production client currently has no shared request pacing;
spacing diagnostic calls does not establish that concurrent production callers are rate-safe.
The earlier quote transport timeout did not recur during spaced post-deployment checks. Its precise
cause remains unproven; neither a credential failure nor a fixed source-code defect was established.
No application code or risk-policy changes were needed for the successful deployment/read checks.

Operational changes were limited to deploying the verified commit, rebuilding/recreating the server,
applying existing migrations, disabling paper submissions, protecting the private environment file,
and spacing verification reads. Shared production request pacing remains a follow-up before
automated/bursty use; any such change must preserve quote freshness and the no-order-retry rule.

## Request pacing deployment — 2026-09-22

The KIS client now serializes token, read and order transport starts through a bounded FIFO gate:
minimum 1.5 seconds between starts, at most eight outstanding requests, and no automatic retries.
Order execution passes a final quote/session callback into the gate. If a queued order becomes stale
or the market closes before dispatch, it is recorded as known-not-sent. Transport timeout, malformed
response or persistence failure remains ambiguous and follows the existing UNKNOWN state.
